## Bounded read contract

Pinned DesktopCommanderMCP **0.2.52**, commit
`c774c3b505de990219637ecdc9a830c8772fae9d`, detects the first two bytes `FF FE`
and reads the remainder as UTF-16LE. Its MIT [text handler](../parity/upstream/src/utils/files/text.ts)
remains an unchanged, hash-verified reference input; the product never imports it.
The original MTerm implementation now exposes that behavior only through
`read_file` and its `read_multiple_files` caller, using the explicit
`FileService.readCompatibilityText` method.

Only the framing BOM is removed. A second or embedded BOM, supplementary Unicode,
and valid replacement-character content remain document text. Odd payload bytes
and unpaired or reversed surrogates fail as `INVALID_UTF16`, with the safe message
`File is not valid BOM-marked UTF-16LE.` Decoded NUL fails as `BINARY_FILE`.
Malformed content beyond the selected page also fails the whole read: MTerm keeps
strict bounded decoding rather than substituting replacement characters.

Without the `FF FE` marker, the existing strict UTF-8 path remains authoritative,
including UTF-8 BOM preservation and malformed/binary diagnostics. No encoding is
guessed from a filename or NUL pattern. Some BOM-less bytes that another producer
might intend as UTF-16 are valid UTF-8; they retain that UTF-8 interpretation.
Native `mterm_read_file`, metadata, search, write, append and edit encodings do not
change. Compatibility writes and edits still refuse existing UTF-16LE documents.
No tool schema, capability, dependency, root policy or remote endpoint changes.

Pagination retains the pinned full/head/middle/tail behavior: CRLF, LF and CR
separate returned lines; a trailing delimiter adds no extra line; negative offsets
ignore `length`; zero-length and beyond-EOF reads return the corresponding status.
Total-line metadata retains the pinned LF-only counting behavior, including its
CR-only quirk. Configured default line limits still apply to ordinary reads.

| Existing limit | Scope retained |
| --- | --- |
| 262,144 raw bytes | Inclusive file ceiling, counting the two-byte BOM; max-plus-one read detects growth |
| 262,144 UTF-8 bytes | All returned multi-file summary and content text, including separators and errors |
| 524,288 serialized bytes | `JSON.stringify(handler result)` in the MCP handler, before outer MCP/RPC fields |

A UTF-16LE BMP document can expand when returned as UTF-8. Exact batch and serialized
result boundaries therefore remain independently tested. The last limit is not a
claim about the final wire-message size, and no new standalone read-text cap was
introduced. Root/private-path/link checks and regular-file checks precede decoding.
Cancellation is checked around open/stat/read work and after handle closure; an
opened handle closes in `finally`, including abort and decoding-failure paths.
These cooperative checks cannot interrupt an OS read already in progress and do
not establish a handle-relative OS sandbox.
